# Инструкции для AI-агента

Этот репозиторий — бакалаврское исследование на основе оригинального [Dualify](https://github.com/timur-harin/dualify). Цель — проверить гипотезы RQ1 поверх его работы, а не изменять базовый метод или создавать промышленную платформу.

## Где находится информация

- [docs/rq1/RQ1.md](docs/rq1/RQ1.md) — **единый источник истины** о гипотезе, методе, данных, метриках, протоколе и терминах RQ1.
- [docs/rq1/tickets/](docs/rq1/tickets/) — шесть последовательных тикетов, каждый со своими критериями готовности.
- [docs/agent/PROJECT_DECISIONS.md](docs/agent/PROJECT_DECISIONS.md) — **глобальная история решений** по всему репозиторию; не удалять и не смешивать с RQ1.
- [docs/agent/KNOWN_BUGS.md](docs/agent/KNOWN_BUGS.md) — **глобальный журнал багов репозитория**, причин и проверенных исправлений.
- [docs/agent/KNOWN_DUALIFY_LIMITATIONS.md](docs/agent/KNOWN_DUALIFY_LIMITATIONS.md) — **отдельный долгосрочный реестр недостатков оригинального метода/статьи Dualify** для отчёта и разговора с руководителем.
- [README.md](README.md), `pyproject.toml` — запуск и структура проекта.

## Работа над тикетами

1. Прочитай этот файл, [протокол RQ1](docs/rq1/RQ1.md), нужные записи из реестров и **один** текущий тикет. Порядок: 01 → 02 → 03 → 04 → 05 → 06. Следующий тикет разрешён только после завершения предыдущего.
2. Сначала изучи существующие функции и тесты Dualify. По умолчанию строй тонкий исследовательский слой поверх исходных extraction, repair, replay, gold scoring и Z3. Меняй их только при конкретной необходимости для RQ1, с тестом и объяснением причины.
3. Работай минимальным сквозным изменением; тестируй наблюдаемое поведение. Для offline-тестов применяй fake/replay clients. Обычно доступны `poetry run ruff check .`, `poetry run mypy src`, `poetry run pytest -q` (сверяй конфигурацию).
4. При новом доказанном баге добавь запись с воспроизведением, причиной, исправлением и результатом проверки в `KNOWN_BUGS.md`. Если найден недостаток **оригинального** Dualify/Z3 — фиксируй его отдельно в `KNOWN_DUALIFY_LIMITATIONS.md` и не меняй oracle без нового решения.
5. При новом подтверждённом проектном решении обнови `PROJECT_DECISIONS.md` с датой и причиной. **Не переписывай реестры после каждого тикета без нового факта.**
6. Зафиксируй изменённые файлы, выполненные проверки и ограничения, затем **остановись на Definition of Done**. Не переходи автоматически к следующему тикету.

**Строгие ограничения:** RQ1 — только генерация и оценка относительно gold, не selection (RQ2) и не fine-tuning (RQ3). Сохраняй исходные p01/p02, validation/repair, Z3 oracle, timeout и исходные 40 benchmark/gold. Никаких gold-подсказок в prompts, секретов в git или использования held-out test для настройки. После dev freeze **обязательно отдельное разрешение** перед test.

## Инженерные принципы: без избыточной сложности

Это **бакалаврский исследовательский проект, а не промышленная платформа**. Главная цель — корректно проверить исследовательские гипотезы, сохраняя воспроизводимость экспериментов. Объём и универсальность кода сами по себе не являются преимуществом.

### Простота прежде всего

- Следуй **YAGNI** и **KISS**: реализуй только то, что необходимо для текущего тикета.
- Выбирай самое простое корректное решение, которое удовлетворяет согласованным критериям приёмки.
- Сначала ищи подходящие функции, модули и интерфейсы в оригинальном Dualify; повторно используй их, если это не усложняет решение.
- Предпочитай небольшие функции и стандартную библиотеку новым слоям абстракций.
- Не создавай универсальные фреймворки, конфигурации и точки расширения ради возможных будущих задач.
- Не добавляй защитную логику для гипотетических сценариев без конкретного риска или требования.
- Не строй отдельную инфраструктуру для одноразовых исследовательских скриптов.
- Если скрипт работает с одним зафиксированным набором данных или seed, храни их как понятные константы, а не как ненужные CLI-опции.
- Опирайся на явные гарантии запуска и формата данных; не добавляй fallback-логику для сценариев, которые не должны возникать.
- Не дублируй проверки между режимами работы и не сортируй данные повторно, если нужный инвариант уже обеспечен и виден из кода.
- Если можно удалить лишний код без потери требуемого поведения, удаляй, а не реорганизовывай его.

### Комментарии и читаемость кода

- В новом и изменяемом коде пиши **понятные комментарии на русском языке**, особенно для алгоритмов, нетривиальных проверок и важных ограничений.
- Простыми словами объясняй **что делает блок кода и зачем**. Если без примера трудно понять логику, добавь короткий пример.
- Комментируй смысловые шаги, а не каждую очевидную строку. Не дублируй код словами и не перегружай файлы комментариями.
- При изменении логики проверяй, что пояснения по-прежнему верны. Для нетривиальных функций можно использовать короткие русскоязычные docstring.
- Код должен быть понятен исследователю, который не участвовал в его написании.

### Контроль области изменений

- Работай только над текущим тикетом; не реализуй будущие тикеты заранее.
- Не рефактори несвязанный код и не добавляй необязательные диагностику, телеметрию или артефакты.
- Не превращай желательные инженерные улучшения в обязательные требования без согласования.
- Явное актуальное решение пользователя имеет приоритет над старыми проектными планами. При противоречии обновляй затронутые документы согласованно, не сохраняя устаревшие требования.
- При упрощении сохраняй научную корректность, воспроизводимость, исходную семантику Dualify и явно согласованные ограничения эксперимента.

### Тесты и критерий остановки

- Проверяй наблюдаемое поведение и важные случаи отказа; не привязывай тесты к внутренней структуре реализации.
- Не добавляй тесты только для поддержки лишних абстракций или гипотетических сценариев.
- Завершай работу, как только выполнен **Definition of Done** текущего тикета.
- Не продолжай «полировку», рефакторинг или расширение функциональности после выполнения критериев.

### Перед реализацией

Перед написанием кода проверь:

1. Это действительно необходимо для текущего тикета или исследовательского вопроса?
2. Нет ли уже подходящего решения в репозитории?
3. Можно ли решить задачу проще — без новых абстракций, конфигурации и инфраструктуры?
4. Что можно удалить или не создавать без потери нужного поведения?

Если дополнительная сложность не оправдана конкретным требованием, **не вводи её**.
