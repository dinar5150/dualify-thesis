# Проектные решения репозитория

**Статус:** исследовательский дизайн утверждён пользователем 2026-11-20. **Основа:** оригинальный `timur-harin/dualify`, commit `7ffd1ae37822096d5b7b573785ee46e877903185`. Здесь ведётся **долгосрочная история решений по всему репозиторию**. Текущая методология RQ1 — в [RQ1.md](../rq1/RQ1.md).

**Утверждённое** решение изменяется только через датированную поправку с объяснением причины и затронутых метрик. Поправки согласуются **до** held-out evaluation и отражаются в спецификации и затронутых тикетах. Фиксируй наблюдения, а не придумывай задним числом обоснования.

| --- | --- | --- |

| D02 | Одна sampling attempt включает полный оригинальный extractor и repair ladder. | Измеряем пригодный итоговый контракт в семантике Dualify; на одну попытку может приходиться несколько LLM-вызовов. |

| D05 | Повышаем температуру initial generation, сохраняя штатный repair. | Получаем разнообразие кандидатов без вмешательства в восстановление; repairs остаются на исходной T=0. |

| D07 | Используем доступную Qwen через Groq, точный model ID фиксируем перед запуском. | Практичность бесплатного тарифа важнее точного совпадения модели из статьи; сравнение разных моделей вне scope. |

| D09 | Основная серия: n=4, k={1,2,4}. | Ограниченный объём эксперимента с Groq Free Tier; более грубые оценки и меньшая статистическая мощность. |
| D10 | Основная метрика — комбинаторный pass@k. | Оценка coverage из фиксированных пулов без зависимости от случайного порядка; first-k — диагностика. |

| D13 | Простые ограниченные retries инфраструктурных ошибок и resume incomplete slots. | Отделяем недоступность провайдера от качества генерации без универсальной системы retry или event sourcing; исключаем resampling-until-valid. |

## Архитектурные решения RQ1

**A01 — Внешний слой оркестрации (запланировано).** Предпочитаем тонкий runner RQ1 и per-attempt client adapter вокруг существующих интерфейсов, а не изменения extractors, prompts или Z3. Интеграция на высоком уровне проще проверяется без изменения исходного поведения. Точечные изменения исходников допустимы лишь при конкретном доказательстве необходимости, отдельном тесте и описании причин.

**A02 — Учёт отдельных candidates (уточнено).** У каждого кандидата уникальный attempt slot, запись фактического вызова, настройки и финальный output. Сохраняем результаты в простом JSONL/slot-files, проверяем число slots и воспроизводим offline-scoring. Полный strict replay внутренних LLM calls и сложный crash-safe ledger не обязательны. Upstream match-by-prompt может повторить прошлый ответ, поэтому один cached output не считается новым sample.

**A03 — Единица статистического анализа (запланировано).** Макроусреднение по benchmark tasks отдельно для каналов; парный bootstrap на уровне задач с фиксированным seed. При 30 test-задачах указывай размер выборки и оговаривай возможную зависимость похожих задач (интервалы могут быть оптимистичны).

**A04 — Происхождение рабочей ветки.** Ветка `dinar5150/dualify-thesis` создана непосредственно от актуального на момент создания upstream commit; старые ветки форка — черновики и не служат источником реализации. Дальнейшая работа следует утверждённой спецификации и зависимостям тикетов.

**A05 — Заморозка оригинального Z3-подхода (утверждено 2026-11-20).** Для эксперимента RQ1 сохраняем семантику solver/checker, исходный timeout 5 секунд, допустимый фрагмент формул, эталонные контракты и штатные extraction/repair. Баги и ограничения оригинальной статьи записываем с доказательствами в [KNOWN_DUALIFY_LIMITATIONS.md](KNOWN_DUALIFY_LIMITATIONS.md) и описываем их влияние на выводы. Не проводим одни и те же исследования повторно и не исправляем базовый метод скрытно. Любое изменение требует отдельного явного утверждения методологии и не входит в существующие тикеты.

## Неопределённые параметры запуска (пока не решения)

- Точный **model ID** Qwen через Groq и наличие требуемой модели/режима.
- Числовая температура initial generation, обоснованная документацией **фактической модели**.
- Действующие лимиты запросов/токенов провайдера, безопасное ограничение частоты и политика retry.
- Seed для split и bootstrap, хеши benchmark — фиксируются до соответствующих live-запусков.

Не подставляй предполагаемые значения. Ticket 05 должен отклонить неполный run manifest.

## История изменений методологии

- **2026-11-22 — упрощение Tickets 02–06, уточнение A02 и D13.** Для исследовательского прототипа достаточно минимальной классификации ошибок и простого resume; вместо обязательного strict replay всех внутренних вызовов сохраняем реальные отдельные attempts и пересчитываем gold scores offline. Ticket 04 сохраняет все научные метрики/unknown bounds и парный bootstrap, но использует простые CSV/JSON/Markdown outputs. Tickets 05–06 сохраняют 100/300 attempts, freeze и отдельное разрешение на test, при этом review проверяет четыре научных инварианта. Исходные Z3, native repair, n=4, отсутствие gold leakage и правила held-out не изменяются. Предыдущие требования к обязательному full transcript replay больше не действуют.

- **2026-11-20 — уточнение D01, D04 и A03.** Отказались от обязательного group-aware split, балансировки и подробного автоматического аудита 40 фиксированных примеров в пользу простого seed-based split и краткой записи рисков. Для 95% интервалов используем paired task-level bootstrap; зависимость похожих задач остаётся **явным ограничением**. Причина: это исследование inference-time sampling, не обучение модели и не проект по построению data-management системы. Предыдущее более сложное требование не действует.
