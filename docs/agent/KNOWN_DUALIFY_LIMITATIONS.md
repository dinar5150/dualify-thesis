# Известные ограничения и сообщения о багах оригинального Dualify

**Область документа:** **оригинальный подход из статьи** и исходная реализация upstream, прежде всего проверка контрактов через Z3 и семантика gold oracle. Этот документ защищает базовый метод исследования от непреднамеренных изменений и избавляет агента от повторной диагностики уже описанных ограничений.

**Исходная ревизия:** [timur-harin/dualify, `7ffd1ae37822096d5b7b573785ee46e877903185`](https://github.com/timur-harin/dualify/tree/7ffd1ae37822096d5b7b573785ee46e877903185). Факты относятся именно к этой версии, а не к старым веткам дипломного форка.

## Обязательные правила для агентов

1. **Сначала проверяй этот реестр**, если работа оригинальных extraction, Z3, формального фрагмента, проверки эквивалентности или gold scoring кажется ошибочной. Прочитай имеющееся воспроизведение и доказательства, прежде чем исследовать поведение заново.
2. **Сохраняй исходную семантику Z3 в дипломном RQ1.** Оригинальные checker, настройки/timeout solver, parser формул, трактовка эквивалентности и reference contracts — **зафиксированные контрольные элементы эксперимента**. Реализация RQ1 может наблюдать исходные статусы и классифицировать их для отчёта, но не должна скрыто менять процедуру доказательства или опровержения формул.
3. **Документируй, не исправляй автоматически.** Если подтвердился новый баг оригинального метода, внеси сюда доказательства, влияние на валидность исследования и вопрос к следующей встрече с руководителем. Предпочитай раскрытие и стратификацию ограничений в отчёте. Изменение исходного подхода требует **отдельно утверждённого методологического решения** и не входит в существующие RQ1 tickets.
4. **Не повторяй уже выполненную диагностику.** Если поведение описано, используй соответствующий ID. Проверяй заново только при появлении новой ревизии upstream или конкретного противоречащего воспроизведения; добавь дату и свидетельства.
5. **Различай** подтверждённое поведение upstream, подозрение, воспроизводимый баг и принятое ограничение исследования. Не называй гипотезу или сообщение пользователя подтверждённым багом без проверки.
6. **Разделяй реестры:** ошибки *нового* RQ1 runner, идентичности кандидатов, политики retries и аналитики записывай в [KNOWN_BUGS.md](KNOWN_BUGS.md). Здесь при необходимости делай ссылку, а не дублируй описание.

Повторяемость проверять по статусам, reasons и агрегатам. |
| DUALIFY-LIM-009 | **Воспроизведено на synthetic fixture Ticket 04 2026-11-22** | При общем предусловии `x == y` исходный checker возвращает `vacuous_equivalence` / `disjoint_post_vocab` для `ret == x + 1` и `ret == y + 1`, хотя проверка несовпадения возвращает `unsat`. | Проверка словаря может отклонить само сравнение при корректных формулах. | Сохранять native reason, учитывать результат как `inconclusive` в границе чувствительности. |
| DUALIFY-LIM-010 | **Воспроизведено на synthetic fixture Ticket 04 2026-11-22** | Для `ret == y + 1` и `ret == Length(y)` с неявным типом `y` исходный checker выводит тип по обеим формулам сразу и возвращает общий `formula_parse_error`. Каждая формула разбирается отдельно. | Сам по себе общий parse error не показывает, что дефект находится в кандидате. | Останавливать offline-анализ с исходным reason, если ошибка не подтверждается при отдельном разборе кандидата относительно типов gold. |
| DUALIFY-LIM-011 | **Воспроизведено на dev gold и минимальном примере Ticket 05 2026-11-22** | `check_equivalence` на контракте `Length(ret[2]) >= 0` против самого себя при `ret: Tuple[int, int, str]` возвращает `formula_parse_error: Non-sequence passed as a sequence`. Исходный `_sort_for_type` строит однородную `SeqSort(IntSort())` по первому компоненту. Исходный gold `parse_input` содержит `Length(ret[2])` и даёт тот же reason при self-comparison. | После завершения dev-генерации все десять результатов `parse_input` имеют статус `unclassified`, по пять в spec и code. | Сохранить Z3 и gold. Согласовать с руководителем, как отразить подтверждённый parse error эталона в итоговой оценке. [Отчёт dev](../rq1/TICKET_05_DEV.md) |

**Оговорка к DUALIFY-LIM-011.** В `parse_input` третий элемент результата имеет
тип `str`, поэтому проверка его длины в эталоне корректна. Для автоматической
оценки этой задачи Dualify должен сохранять тип каждой позиции неоднородного
кортежа при переводе контракта в Z3. Такое изменение проверяющей системы требует
отдельного методологического согласования. Если оно одобрено, сначала нужно
проверить эталон сравнением с самим собой, затем переоценить десять уже
сохранённых результатов offline. Повторная генерация для этого не требуется.
Если исследование сохраняет исходный Dualify, `parse_input` следует явно
учесть как задачу с непроверяемым эталоном по согласованному правилу оценки.

## Подтверждённые баги оригинальной статьи/метода

**Дополнительные баги для этого раздела пока не предоставлены пользователем и не воспроизведены независимо.** Пользователь планирует обсудить конкретные ошибки на следующей встрече с научным руководителем. Добавляй их **после получения свидетельств**, не делая выводов из таблицы ограничений или старых черновых веток.

На каждую проблему используй отдельную запись:

### DUALIFY-BUG-NNN — <краткое и точное название>

- **Статус:** сообщено / ожидает воспроизведения / воспроизведено / обсуждено с руководителем / принято как ограничение / одобрено отдельное исследование
- **Происхождение:** утверждение статьи, оригинальный код или поведение benchmark
- **Исходная ревизия и компонент:** точный commit и участок
- **Дата сообщения / последней проверки:** даты
- **Наблюдаемое поведение:** вход, ожидаемый результат, фактический результат, исходный Z3 reason/diagnostics
- **Минимальное воспроизведение:** команды, fixture, версия solver и timeout (если применимо)
- **Важность:** влияние на эквивалентность, gold score, канал или научный вывод
- **Доказательства:** log, test, screenshot, ссылка на код или заметки встречи
- **Учет в RQ1:** указать в отчёте / стратифицировать / оговорить ограничение; сохраняется ли валидность эксперимента
- **Решение и ответственный:** решение пользователя/научного руководителя, дата, возможный отдельный тикет
- **Изменена ли оригинальная реализация Z3?:** **Нет** в рамках утверждённого RQ1
- **Повод для новой проверки:** конкретная новая информация, требующая пересмотра вывода

## Материалы к встрече с руководителем

Перед следующей встречей собери нерешённые записи **DUALIFY-BUG-NNN** в краткие вопросы с доказательствами. После встречи внеси сообщение пользователя и решения руководителя. Не изменяй оригинальный checker вместо обсуждения.

Правила эксперимента изложены в [протоколе RQ1](../rq1/RQ1.md), причины решений — в [PROJECT_DECISIONS.md](PROJECT_DECISIONS.md).
