# RQ1: repeated sampling and pass@k

Эта реализация проверяет, помогает ли многократная генерация получить хотя бы один контракт, который Dualify **доказал эквивалентным gold**. Мы не выбираем лучший контракт из нескольких. Это будет отдельная задача RQ2.

## Какие файлы добавить

Распакуй архив в **корень репозитория** `dualify-thesis`, сохранив структуру папок:

| Файл | Назначение |
| --- | --- |
| `src/dualify/rq1_sampling.py` | Повторные запуски, оценка кандидатов, расчёт pass@k, запись результатов |
| `scripts/run_rq1.py` | Командная строка для RQ1 |
| `tests/test_rq1_sampling.py` | Тесты без обращений к LLM |
| `docs/rq1_sampling.md` | Эта инструкция и методология |

**Существующие файлы заменять не нужно.** `runner.py`, p01, p02 и алгоритмы Z3 остаются прежними. Требуется актуальная `main` после PR #2, где уже есть `benchmark/dev_small` и очищенные исходники.

## Как запустить

Из корня проекта (WSL/Ubuntu):

```bash
poetry install
poetry run pytest -q tests/test_rq1_sampling.py
```

Сначала короткая проверка с двумя сэмплами. Она обращается к API и расходует токены:

```bash
poetry run python scripts/run_rq1.py --num-samples 2 --temperature 0.7
```

Затем пилот для RQ1, восемь сэмплов на каждую из шести задач:

```bash
poetry run python scripts/run_rq1.py --num-samples 8 --temperature 0.7
```

`GROQ_API_KEY` должен быть установлен в окружении или в `.env`. Если задан `DUALIFY_API_KEY`, Dualify использует его с более высоким приоритетом. Не помещай ключ в скрипт или команду.

По умолчанию модель `qwen/qwen3.8-27b`, endpoint `https://api.groq.com/openai`, benchmark `dev_small`, а значения k — 1, 2, 4, 8 (из них автоматически выбираются только k ≤ n). Если провайдер изменил идентификатор модели, передай актуальный через `--model`.

Другие параметры:

```bash
poetry run python scripts/run_rq1.py \
  --num-samples 8 --temperature 0.7 \
  --ks 1 2 4 8 \
  --output-dir results/my_rq1_run
```

Папка `--output-dir` должна быть пустой. Без этого параметра скрипт создаёт папку с уникальной временной меткой под `results/`.

## Как устроена генерация

Для каждой попытки скрипт запускает **тот же `run_experiment()`**, что и обычный `dualify-run`. Внутри каждой задачи сохраняется прежняя последовательность:

1. p01 строит контракт по текстовому описанию. При ошибке работает существующий repair.
2. p02 строит контракт по исходному коду. Repair тоже остаётся включённым.
3. Dualify сравнивает p01 и p02, выполняет планирование действий и оценивает финальные контракты по gold.
4. Отдельно оцениваются **первоначальные** формулы из `extraction_trace.initial`, до repair.
5. Скрипт повторяет весь pipeline `n` раз при одинаковых настройках, собирает результаты и считает pass@k.

`--temperature 0.7` применяется ко **всем LLM-вызовам** во время попытки, включая repair и action planning. Это pass@k **полного pipeline**, а не чистой модели без repair. Нельзя напрямую сравнивать его `pass@1` с предыдущим baseline при температуре 0.0 как две оценки одной и той же конфигурации.

Каждый повторный запуск делает новые обращения к API. Это даёт стохастические попытки при `temperature > 0`, но не гарантирует, что ответы будут различаться или что провайдер использует независимые генераторные seed. **Replay** только воспроизводит записанные ответы, а не создаёт новые сэмплы.

## Как считается pass@k

Пусть для одной задачи мы получили `n` кандидатов, из которых `c` прошли выбранный критерий успеха. Оценка:

\[
\operatorname{pass@k} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}.
\]

Например, при `n=8` и `c=2`:

- `pass@1 = 2/8 = 0.25`;
- `pass@2 = 1 - (6/8) * (5/7) ≈ 0.4643`;
- `pass@8 = 1`.

Это **oracle pass@k**: качество каждого кандидата определяет gold-оценщик. В реальном использовании gold недоступен, поэтому `pass@k` не показывает, умеет ли система найти лучший кандидат среди нескольких. Это цель RQ2.

**Строгий критерий успеха в этой реализации:** сравнение с gold вернуло `contract_equivalent=True`, постусловие не вырождено (`ret == ret`, `True` и подобные), и кандидат не подставлен из заранее прописанного fallback. Статус `degraded` не является автоматическим провалом: после `safe_repair` контракт всё ещё может быть доказанно эквивалентным. `solver_unknown` считается *неподтверждённым успехом*, но отдельно учитывается в диагностике. `generated_stronger` и `generated_weaker` сохраняются, но не считаются эквивалентностью.

Мы считаем `pass@k` **отдельно** для p01 и p02 и **отдельно** для initial/final. Усреднение по задачам — обычное арифметическое среднее, каждая задача получает одинаковый вес. Шесть задач — только пилот; на этом объёме нельзя делать сильные статистические выводы.

## Что сохраняется

Новая папка `results/rq1_dev_small_<UTC>/` содержит:

| Путь | Содержимое |
| --- | --- |
| `metadata.json` | Модель, benchmark, температура, n, k, Git-коммит, статус завершения, SHA256 manifest |
| `transcript.jsonl` | Все запросы к модели, ответы, температуры и хеши промптов |
| `runs/sample_001/*.json` и т. д. | Полные отчёты существующего Dualify, включая repair-трассы |
| `samples.json` | Первоначальные и итоговые формулы каждого кандидата, результаты сравнения с gold |
| `candidates.csv` | По одной строке на канал, стадию, задачу и попытку |
| `metrics.json` | pass@k для каждой задачи, среднее по задачам и распределение исходов |
| `pass_at_k.csv` | Таблица pass@k, которую удобно строить в графики |

В `samples.json` задачи имеют **полный `gold_benchmark_id`**, чтобы две разные функции `double` не объединились в одну. В транскриптах сохраняются промпты и ответы. Не загружай их в публичный репозиторий без проверки содержимого.

## Replay и продолжение прерванного запуска

В каждом обычном запуске transcript записывается автоматически. Чтобы воспроизвести его без обращений к API:

```bash
poetry run python scripts/run_rq1.py \
  --num-samples 8 --temperature 0.7 \
  --replay results/rq1_dev_small_ВРЕМЯ/transcript.jsonl
```

Параметры, последовательность вызовов и промпты должны совпадать. Скрипт дополнительно проверяет температуру и метаданные модели/провайдера. Если после обновления Dualify поменяются промпты или порядок вызовов, replay может завершиться ошибкой.

Если live-запуск оборвался, можно повторить его с теми же параметрами, используя сохранённый транскрипт. Успешные вызовы из его начала будут считаны с диска, а новые вызовы допишутся:

```bash
poetry run python scripts/run_rq1.py \
  --num-samples 8 --temperature 0.7 \
  --resume-transcript results/rq1_dev_small_ВРЕМЯ/transcript.jsonl
```

Для resumed run создаётся **новая папка результатов**; незавершённый отчёт остаётся для диагностики. Пользуйся resume только с той же версией кода и исходными данными.

## Что пока не входит в RQ1

Не реализованы выбор лучшего кандидата, self-consistency и дополнительные проверки кандидатов без gold. Их нельзя добавлять к пилоту, не изменив условия эксперимента. Запуск на `lifted_auto_eval_clean` блокируется без явного `--allow-holdout`; оставшиеся 34 задачи следует использовать для итоговой оценки после фиксации метода.

Ограничения оценщика остаются: `solver_unknown` может скрывать корректный контракт; сильный контракт может не быть эквивалентен слабому gold. Поэтому в отчётах нужно показывать и `pass@k`, и долю `unknown`/отношения силы контрактов.

Для финального запуска на всех 40 задачах добавляется `metrics_holdout.json`, рассчитанный **только по 34 отложенным задачам**. При этом `metrics.json` содержит все 40 задач. Не используй holdout-результаты для последующего выбора температуры или изменения промптов.
