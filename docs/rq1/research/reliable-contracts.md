## Краткие итоги

- Доказана семантическая ошибка в трансляции Python `//` и `%` для отрицательного делителя. Генератор на основе AST устранил 38 расхождений по фактическому возврату в парном контроле на 2 538 входах. Проверка неизменным gold scorer подтвердила 7 из 8 формул. На восьмой формуле оба проверяющих запроса сохранили статус `unknown`; алгебраическая проверка и исполнение поддерживают формулу.
- Предварительная валидация в исходном pipeline повреждала вызовы внутри формул. Комбинация двух локальных правок сохранила правильное свойство длины `zipped_pairs` при исходном scorer. Та же комбинация ухудшила контракты `next_departure` из-за несовместимой проверки делителя. Массового включения этих правок без проверки траектории repair результаты пока не обосновывают.
- На тех же 100 архивных кандидатах представление разнородного кортежа позволило вынести 10 отрицательных решений вместо ошибок разбора. Локальная развёртка кванторов дала контрпримеры ещё для 10 исходных `unknown` на `csv_first_column`. Обе правки повысили проверяемость. Число подтверждённых совпадений с историческим gold от них не выросло.
- На восьми новых скалярных задачах исправленный валидатор поднял число точных нативных контрактов с 0 до 8 из 16 при общем initial на каждой паре. Проверка исходным scorer дала те же числа. Шесть конкретных контрпримеров, переданных Qwen, не привели ни к одной точной ревизии. Судьи иногда обращали verdict при смене источника или оформлении; из 72 предложений на контрольных парах подтверждены 43.
- Для диплома рекомендован эксперимент о надёжности генерации и проверяемости контрактов с фиксированным сравнением против независимых попыток. Архивный pass@k остаётся точкой сравнения; задачи с неполным описанием и спорным gold требуют явного правила трактовки до любого held-out. [Литература и сравнение направлений](literature.md)

Новые задачи — диагностические, без встроенных формальных аннотаций. Они целенаправленно охватывают пограничные случаи и ограниченный фрагмент, поддерживаемый экспериментальным анализатором. Они не оценивают частоту этих случаев среди произвольных Python-программ. Код и NL описывают одну и ту же целевую функцию; компилятор получает только код, p01 только текст и подпись, p02 только код и подпись. Эталонные формулы хранятся для оценки. В p01 при проверке используется отдельный список примеров, выведенных из описания; в p02 примеры получают запуском функции. [Новые задачи](../../../scripts/research/contract_cases.py) · [Тесты компилятора](../../../tests/test_research_codegen.py)

Главные метрики для прямого сравнения генераторов — доказанная точность домена и постусловия в фиксированном скалярном DSL, затем исходный scorer как сопоставимая метрика. Проверка исполнением отдельно считает расхождения домена, отклонение фактического возврата и принятие пробного неправильного возврата. Формальная проверка ищет SAT для XOR предусловий и отдельно для XOR постусловий под эталонным доменом. Конечный перебор выявляет контрпримеры на проверенных входах. Для формул из разных фрагментов он даёт разное покрытие. `unknown`, неподдерживаемая формула и доказанное различие учитываются отдельно.

## B. Что доказывает oracle

### Прямые проверки

Сравнение строит запросы на существование входа, а для постусловия ещё и результата, на которых формулы имеют разные истинностные значения. В поддерживаемой модели `unsat` такого запроса исключает различие. `sat` даёт возможный контрпример, который следует проверить относительно семантики Python и принятых предположений. `unknown` оставляет запрос открытым. Теории строк, последовательностей, кванторов и нелинейной арифметики влияют на то, какой ответ solver способен получить.

Контроли включили тождество, алгебраическое преобразование, эквивалентность под общим предусловием, strengthening и weakening, несовместимые формулы, тавтологию, противоречие, пустой домен и неподдерживаемые операции. Для `x == y` и постусловий `ret == x + 1` / `ret == y + 1` прямой XOR под предусловием дал `unsat`, а исходный checker отклонил доказательство по словарю. При одинаковом `ret == x` и списках предусловий `[x >= 0, x < 0]` и `[]` checker вернул `equivalent_no_mismatch`. Прямой XOR дал `sat`: удаление обоих конъюнктов изменило домен. Заданная таким способом несовместимая пара отделяет ошибку обёртки от поведения решателя. [Контрольные запросы](artifacts/oracle-audit.json) · [Обнаруженные ограничения](../../agent/KNOWN_DUALIFY_LIMITATIONS.md)

В отдельном тесте pigeonhole увеличение бюджета позволило доказать `unsat`, а запрос с вещественным переменным показателем `2**a == 3` вернул `unknown`. В `csv_first_column` даже подстановка одного элемента в формулу с квантором сохранила `incomplete (theory seq)`. Для конкретного входа `["a,b"]` внеиндексные обязательства проверены отдельно и кванторы развёрнуты. Пять spec-кандидатов допускают неверный результат `["x"]` вместо `["a"]`; пять code-кандидатов отвергают валидный вход из-за формы квантора. Все десять контрпримеров дали `sat` после эквивалентной локальной редукции. [SMT-обязательства и причины unknown](artifacts/oracle-audit.json)

Есть отдельные расхождения между SMT и Python: отрицательный делитель для `//` и `%`, Python `/` над целыми, индексация `xs[-1]`, `isdigit` на Unicode и пустой строке, кодирование `None` пустой последовательностью. Последнее присутствует в dev gold `solve`. Утверждения о полноте эквивалентности в Python возможны только после проверки используемой кодировки. [SMT-LIB Ints](https://smt-lib.org/theories-Ints.shtml) · [Z3 Sequences](https://microsoft.github.io/z3guide/docs/theories/Sequences/) · [Python Expressions](https://docs.python.org/3/reference/expressions.html)

### Альтернативные правила на одних кандидатах

Эквивалентность характеризует совпадение с выбранным эталоном. Для контракта refinement понятие точности иное: кандидат принимает все входы эталона и обещает на них как минимум свойства эталона. Направления домена и постусловия проверяются раздельно. Введены дополнительные обязательства о непустом домене, наличии допустимого результата для каждого входа и наличии результата, который постусловие исключает. Эти обязательства ловят часть вакуозности. Они сами могут оказаться сложнее строгого сравнения, особенно со строками и кванторами.

| Правило и те же 100 финалов | Подтверждено | Опровергнуто | Не определено solver | Ошибка разбора |
| --- | ---: | ---: | ---: | ---: |
| Исходная оценка dev | 13 | 67 | 10 | 10 |
| Прямые XOR с той же трансляцией | 13 | 69 | 8 | 10 |
| Эквивалентность с nonvacuity и feasibility | 0 | 69 | 21 | 10 |
| Refinement с nonvacuity и feasibility | 13 | 55 | 22 | 10 |
| Прямой XOR + разнородный кортеж для `parse_input` | 13 | 79 | 8 | 0 |
| Дополнительно конкретные контрпримеры `csv_first_column` | 13 | 87 | 0 | 0 |

Последняя строка объединяет два локальных эксперимента с непересекающимися строками, для остальных случаев используется прямой XOR. Она описывает покрытие решения на этом архиве. Строки refinement и эквивалентности отвечают на разные вопросы. Два общих offline-прохода прямого XOR дали 67–69 отрицательных решений и 8–10 `unknown`. Число доказанных совпадений не менялось. В обоих проходах локальные свидетели разрешили все десять CSV-строк. Из 13 положительных решений refinement ни одно не совпало с 13 положительными решениями исторической эквивалентности. Например, слишком сильное `ret == expr` для `extract_expression` имплицирует слабое свойство gold, но отвергает фактический результат `"a"` на `"(a)"`. Refinement также допускает константы 0 и 1 при слабом диапазоне `determine_column`. Переход 13 успехов в `unknown` при проверке feasibility показывает стоимость доказательства, а архивные формулы остались прежними. [Результаты по слотам](artifacts/oracle-audit.json) · [Реализация](../../../scripts/research/oracle_audit.py)

У `parse_input` смешанный тип реализован локально Z3 TupleSort с отдельной проекцией для каждой позиции. Проверка эталона с собой проходит, а контроли неверной ширины и непрямоугольной карты различимы. Десять сохранённых финалов с пустым доменом и `ret == ret` опровергнуты. Повышение выразимости и проверяемости здесь доказано отдельно от качества генерации. ### Качество эталонов и переносимость

| Задача dev | Независимое наблюдение | Влияние на оценку |
| --- | --- | --- |
| `solve` | `solve([5,5,10],2)` возвращает `(2,10)`; код запрещает равные значения в паре, gold запрещает только одну и ту же позицию | Совпадение с gold и соответствие коду расходятся |

## C. Контроль LLM-as-a-Judge

Верифицированы шесть положительных и шесть отрицательных контрактов. Независимый XOR и запуск Python подтверждают метки. Обе judge-модели получают либо NL и подпись, либо Python и подпись, а также два контракта с обезличенными позициями A/B. Требуются отдельный verdict для каждого, сравнение и конкретный свидетель ошибки. Смена канала, перестановка, повтор и два изменения оформления дают шесть запросов на пару в каждой модели. Qwen работала с `reasoning_effort=none`, GPT-OSS с `low`, обе при `T=0`. Gold, метка и происхождение пары в запрос не передаются. [Фикстуры](../../../scripts/research/judge_cases.py) · [Дизайн](../../../scripts/research/judge_run.py)

Контроль fallback запущен на двух реально сохранённых `csv_first_column` с историческим `unknown`, по одной траектории на канал. Обе модели дали FAIL обоим контрактам, но ни один из четырёх предложенных свидетелей не прошёл независимую проверку. В spec обе модели указали `["a"]` как неверный возврат для `["a,b"]`, хотя именно его возвращает функция. Для code нужна проверка того, что кандидат исключает допустимый **вход**. Пилот поддерживает роль judge как источника гипотез с отдельной верификацией. Данных для использования его verdict как основного oracle, решающего fallback или рабочего selector недостаточно. ### Исправление предварительной валидации

Факторы — непустой служебный ID только в type-check и допуск `Char`/`String` в обоих extractors. Эталонный scorer и финальные условия проверки остаются историческими. ### Генерация из типизированного Python AST

У поддерживаемых функций компилятор выводит предусловие как объединение путей с нормальным возвратом и формулирует значение результата под соответствующей ветвью. Необходимая область включает отсутствие деления на ноль на исполняемом пути. Компилятор принимает только исходный код, использует `int` и `bool` и воздерживается при неподдерживаемой конструкции. Для пути с отрицательным делителем перевод `a // b` использует SMT-деление `(-a) / (-b)` с положительным знаменателем. Аналогичный перевод остатка меняет знак соответствующего SMT-остатка. Вычисление затем проверяется в том же DSL и у того же scorer, которые применяются к генерациям модели. [Реализация](../../../src/dualify/research_codegen.py) · [Тесты переноса и отказа](../../../tests/test_research_codegen.py)

| Компиляция на 8 скалярных задачах | Типизированный XOR | Исходный scorer | Допустимый фактический возврат отклонён | Пробный неверный возврат допущен |
| --- | --- | --- | ---: | ---: |
| Прямой SMT-перевод `//` и `%` | 6 точных, 2 опровергнуты | 6 эквивалентны | 38 | 18 |
| Семантика Python | 7 точных, 1 unknown | 7 эквивалентны, 1 unknown | 0 | 0 |

Оба варианта проверены на 2 538 входах, из них 1 451 допустимый, и 2 442 пробных неправильных возвратах. Прямой перевод на `signed_bucket(5,-2)` задаёт  `-2` вместо `-3`, а на `signed_remainder(7,-3)` — `1` вместо `-2`. Контроль меняет только lowering арифметики. Для неизвестной формулы остатка при `b<0` положим `d=-b`, `q=floor((-a)/d)`. Тогда отрицание SMT-остатка равно `-((-a)-d*q)=a-b*q`, что согласуется с эталонным определением. При `b>0` достаточно обычного SMT-остатка. Доказательство арифметического тождества не заменяет зафиксированный результат solver. В замороженном dev покрыта 1 из 10 задач — извлечённое скалярное тело `duration`. Компилятор восстановил точный возврат и широкий домен тела. Остальные отказы явно записаны, в том числе локальная переменная в `next_departure`. Этот результат ограничивает обобщение на реальные функции. Независимый рецензент построил 58 дополнительных программ и проверил 42 282 входа, из них 36 661 нормальный возврат и 5 621 исключение, без расхождений. Проверка охватывает конкретную синтетическую область. [Дифференциальная проверка](../../../scripts/research/review_compiler.py) [Артефакт сравнения](artifacts/live-analysis.json)

### Проверяемая обратная связь против повторной попытки

У каждой из 16 пар задача–канал одна общая начальная генерация Qwen из штатного текста p01/p02, `T=0.7`. Продолжения израсходовали по одному вызову. Порядок задач и продолжений перемешивался с seed `20261125`. Fresh повторяет первый запрос с новой выборкой. Revision заново анализирует формулу, сохраняя исходный запрос и ответ в истории. Witness добавляет к тому же контексту проверенный пример и уточнение о семантике целочисленного деления. При ошибке типа он получает сообщение парсера; при отсутствии найденной проблемы промпт совпадает с revision. Ни одному из continuations не передаётся формула gold. Область проверки code охватывает сетку `[-4,4]` по каждому аргументу. Spec использует только независимо записанные примеры, согласованные с текстом задачи. Токены, задержки и физические запросы учитываются отдельно. [Генератор](../../../scripts/research/generation_run.py) · [Оценка](../../../scripts/research/live_analysis.py)

## H. Решение по направлению диплома

| Направление | Оценка научной применимости |
| --- | --- |
| Multiple sampling | Повторимая архивная точка сравнения с низкой самостоятельной новизной. На dev один прирост из девяти задач и нестабильный oracle. Для новой серии нужен одинаковый бюджет и исправление оценки до held-out |
| Надёжная генерация формальных контрактов | Подтверждённые механизмы ошибок и ограниченный прототип. Можно измерять поддержку типов, точность результата, частоту abstain и цену repair при фиксированном scorer. Реалистично для бакалаврской работы при явно узкой области |
| Verification-guided refinement | Исследовательский вопрос сосредоточен на том, какой вид верифицированной обратной связи даёт выигрыш при равном бюджете. Есть близкие исследования на других языках и формализмах. Неопределённость эффекта требует новых независимых семейств задач |
| Корректность автоматической оценки | Есть собственные воспроизводимые контрпримеры к обёртке и к gold, а также решения на тех же ответах. Сильное альтернативное направление, если ключевой вклад диплома — методика измерения. Нужна независимая разметка критериев soundness и полноты |
| Hybrid verification | Контрпример от выполнения или SMT обеспечивает научно ясную отрицательную проверку. Judge добавляет непроверенные гипотезы и затраты. Широкая замена oracle увеличивает риск ошибочного положительного результата |
| Разделение намерения и реализации | Объект исследования — согласованность двух спецификаций с разными источниками доступной информации. Примеры `duration` и `next_departure` дают основание для теста на скрытые инварианты. Для него нужна отдельная разметка информационной достаточности и спорных доменов |

**Рекомендация руководителю.** Сохранить исходный RQ1 как завершённый dev-ориентир и сформулировать следующий исследовательский вопрос так: «Как типизированное представление Python влияет на точность, проверяемость и покрытие автоматически полученных контрактов при фиксированной системе оценки?» Оценить генераторы при фиксированном evaluator и evaluator при фиксированных кандидатах. Проверяемую обратную связь оставить отдельным сравнением при равном бюджете, поскольку шесть подтверждённых свидетелей не дали точной ревизии в пилоте. Для расширения за пределы малых скаляров предварительно согласовать контекст, семантику исключений, проверяемые типы и независимую разметку. Для неизменного held-out потребуется отдельное разрешение и протокол, утверждённый до вскрытия данных. poetry run python scripts/research/pipeline_audit.py --score-workers 6 \

  results/research-replay/live /tmp/dualify-live-analysis.json

  results/research-replay/live /tmp/independent-live-review.json

poetry run ruff check src tests scripts/research
poetry run mypy src tests
