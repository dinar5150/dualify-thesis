# RQ1 Ticket 05 — dev campaign и freeze

## Итог 2026-11-22

**BLOCKED**. Завершены **65 из 100** слотов. Есть шесть полных задач и
пять завершённых spec-слотов задачи `parse_input`. На её code baseline Groq
дважды вернул HTTP `429` с дневным пределом в 200 000 токенов. Кампания
остановилась после двух разрешённых отправок этого вызова. Из бюджета
в 180 POST использованы 179, включая 13 ответов `429` и два HTTP `400`,
подтверждённых как ошибки формата ответа модели. Кампания заняла 56 мин 14 с.
В завершённых слотах записаны 166 логических вызовов, включая 101 repair.
В 46 слотах сохранён результат с признаком native degradation.

Два offline-пересчёта дали одинаковые oracle status и reason для 65
кандидатов и одинаковые метрики по полным задачам. Команда полного
offline-отчёта вернула `BLOCKED` с перечислением недостающих слотов первого
неполного пула. Полный pass@k, прирост и доверительные интервалы по десяти
задачам требуют оставшихся 35 слотов.

У пяти завершённых spec-кандидатов `parse_input` статус `unclassified`.
Исходный oracle возвращает `formula_parse_error: Non-sequence passed as a sequence`
даже при сравнении gold с самим собой. В исходном checker тип
`Tuple[int, int, str]` отображается в однородную последовательность
целых, поэтому `Length(ret[2])` невозможно разобрать. Эта ошибка разбора
требует методологического решения перед held-out.
[DUALIFY-LIM-011](../agent/KNOWN_DUALIFY_LIMITATIONS.md)

Freeze содержит точные ревизии и параметры. Архив содержит исходный
preflight, полный список слотов в `gate.json`, candidate records, HTTP-ответы и
`partial-scores.json`. В копии для репозитория скрыт идентификатор организации
Groq в текстах ошибок. Held-out запросов — 0.
[Freeze manifest](artifacts/dev-2026-11-22-freeze.json) ·
[Архив кампании](artifacts/dev-2026-11-22.tar.gz)

## Возобновление dev-прогона

По решению пользователя от 2026-11-22 общий предел в 180 POST снят.
Продолжение использует уже сохранённые 65 попыток и тот же план из 100
слотов. Новый preflight сохраняется в `resume-preflight.json`, исходный
остаётся доступен для проверки первого этапа. Groq применяет свою квоту,
а клиент использует прежние ограничения на частоту и число повторов
одного вызова.

## Запуск и воспроизведение

Для локального запуска используйте чистый checkout на зафиксированной ревизии.

```bash
poetry run pytest -q
poetry run python scripts/prepare_rq1_split.py --check
poetry run python -m dualify.rq1_dev results/rq1-dev-2026-11-22
```

Команда использует `GROQ_API_KEY` из окружения или локального `.env` и
проверяет доступность модели по `GET /models`. До запроса записывает
`preflight.json` с ревизией, версиями, SHA-256, split и 100 slot IDs.
Конфигурация привязана к каталогу кампании. Повтор команды с тем же каталогом
пропускает завершённые слоты и допускает продолжение после классифицированного
инфраструктурного сбоя. При оборванной записи с HTTP-следом и без диагноза
следующая попытка блокируется.

```bash
poetry run python -m dualify.rq1_dev results/rq1-dev-2026-11-22 \
  --offline results/rq1-dev-reproduction
```

Offline-команда сверяет split, конфигурацию пулов, ревизии файлов scorer,
версию Z3 и HTTP-записи завершённых slots. Затем запускает gold scoring с
десятью dev-эталонами. Сравниваются итоговые метрики, oracle statuses и
reasons. Конкретные значения контрпримеров Z3 могут варьироваться.
[Реестр ограничений Dualify](../agent/KNOWN_DUALIFY_LIMITATIONS.md)

## Конфигурация Groq

- Модель `qwen/qwen3.8-27b`, instruct через `reasoning_effort=none`, chat
  completions с `response_format=json_object`. Baseline и repair используют
  `T=0`, initial treatment использует `T=0.7`. Groq применяет свой default
  `top_p=1`. [Groq](https://console.groq.com/docs/model/qwen/qwen3.8-27b) ·
  [Qwen](https://huggingface.co/Qwen/Qwen3.8-27B)
- В HTTP payload baseline и repair записано ровно `0`. Groq документирует
  внутреннее преобразование этого значения в `1e-8`.
  [Совместимость Groq](https://console.groq.com/docs/openai#temperature)
- Первый этап применял предел в 180 POST. Максимум 1024 output tokens
  за запрос. Интервал между POST составляет минимум 18 секунд, timeout
  запроса 120 секунд. Для сетевой ошибки, 429 и 500/502/503/504 клиент
  допускает две физические отправки на логический вызов с backoff от 2 до
  60 секунд. [Лимиты Groq](https://console.groq.com/docs/rate-limits)
- Время попытки включает ожидание и backoff. Чистое inference time остаётся
  NA. Отчёт отдельно показывает логические вызовы и фактически наблюдавшиеся
  POST. Абсолютная квота зависит от настроек организации Groq.

## Сквозной пример

В PEP316-задаче `arith.py::swap` исходная спецификация описывает перестановку
двух элементов. Четыре отдельные treatment attempts канала spec сохранили
одну и ту же итоговую формулу `And(ret[0] == things[1], ret[1] == things[0])`.
У каждой попытки был отдельный ответ Groq. Один из четырёх слотов потребовал
repair при `T=0`. Offline scorer сравнил каждый сохранённый контракт с gold
этой задачи. Исходный Z3 вернул `equivalent_no_mismatch` для всех четырёх.
При `c=4` и `u=0` обе границы pass@1/2/4 равны `(1, 1, 1)`. В code
получился тот же итог после штатных repairs. Формула совпадает во всех
четырёх treatment slots каждого канала, поэтому в этой задаче увеличение k
не даёт прироста.

Пример воспроизводится из сохранённого пула командой ниже.

```bash
case_file=crosshair_examples_PEP316_correct_code_arith.py_swap
dev_gold=$(mktemp -d)
cp "benchmark/lifted/$case_file.yaml" "$dev_gold/"
poetry run python -m dualify.rq1_report \
  "results/rq1-dev-2026-11-22/pools/$case_file" \
  --gold-dir "$dev_gold" --output-dir results/rq1-dev-swap-reproduction
```

## Независимое ревью

| Ось | Проверили | Исправили |
| --- | --- | --- |
| Standards | Простоту оркестрации, целостность gate и лимит при конкурентном запуске | Повреждённые записи входят в диагностику BLOCKED. Эксклюзивная блокировка каталога проверена двумя процессами. |
| Spec | Отдельные обращения, путь исходных данных к p01/p02, gold только при scoring, исходный Z3 и формулы pass@k/unknown | Offline scoring сверяет сохранённые ответы с HTTP-записями и проверяет уникальные completion IDs. Resume после неоднозначного POST блокируется, предыдущий диагноз архивируется до повторной отправки. |

У каждой задачи в каждом канале есть один baseline и четыре treatment slots.
Текст prompts строят штатные p01/p02 из полей benchmark и событий текущего
repair. Оценку проводят исходный Z3 и формулы pass@k из Ticket 04.
Контрпримеры solver интерпретируются только в поддерживаемом фрагменте.
Репетиции исходных формул и похожие задачи могут влиять на разнообразие и
доверительные интервалы. [Аудит benchmark](TICKET_01_RISKS.md) ·
[Протокол и ограничения](RQ1.md)

Перед первым запросом прошли 164 теста, один был пропущен. После исправлений
ревью прошли 168 тестов с одним пропуском, mypy для `src tests`,
Ruff для `src tests` и проверка benchmark manifest. Полный Ruff выдаёт
те же 172 нарушения в старых файлах, что и на исходном `main`.
